# BPMN authoring

## When to use

The user wants a new approval flow, an extra review step, different reviewers per step, or conditional routing — anything that changes **the order things happen** rather than the logic inside a step.

**Sample prompts**

1. Add a second review step to our DCR approval flow, with a different role reviewing after the first approval.
2. Create a new BPMN for a potential-match review that routes to Merge or Not-a-Match based on the reviewer's decision.
3. I have a workflow that deploys but the task never shows up for anyone — what's wrong?

## Inputs

1. **`references/bpmn-rules.md`** (beside this file) — read it **before** writing any XML. It is the deny-list and validation checklist, not background reading. Most of §10 is now enforced by the editor as you type (see Procedure 7), so it is what you write *from*, not what you grade yourself against afterwards. Its §12 "Known Ambiguities" lists what is confirmed against Reltio's own source/docs versus this team's inference from observed deploy behavior — read it before stating any rule as unconditional. Its §14 lists all 4 fixed OOTB workflows (not just DCR) and how each one actually triggers — read it before customizing PMR, Delete, or Authoring, since the same "keep the id or the UI stops auto-triggering it" rule applies to all four, and Delete's id is the one known to vary by tenant (`deleteReview` vs. `recommendForDelete`). Its §15 has real skeletons for multi-instance quorum review and timer-based escalation — both BPMN-only for the voting/escalation shape itself, so check there before defaulting to "needs Java" on either.
2. **`references/reltio-doc-portal-reference.md`** (beside this file) — the citable, official Reltio doc-portal pages and the public `github.com/reltio-ai/workflow` source repository for this domain. If it and `bpmn-rules.md` disagree, the official source wins; say so rather than picking a side silently.
3. The tenant's deployed definitions (**Workflows → Process Definitions**) and the roles that exist on it, for `candidateGroups`.
4. **Five facts, gathered rather than interrogated** — take what the user's message and the workspace already say, and ask **only for what cannot be inferred, in a single message, before you start** (never one question per turn). *Which tenant?* (drafts live under one tenant and deploy to it; with one connected, use it and say which). *New workflow, or a copy of an existing one?* (a copy inherits working structure and is usually the right start). *Which workflow is being copied?* (ask by name only if the user was approximate — never guess between two similar ids). *What is the display name?* (free text; default it to the id and say so). *Draft only, or deploy as well?* (deploying writes to a live tenant — never assume; the deploy modal is the confirmation). The one question the final reply asks is the PR question, at the end, when Java is involved; everything above is settled before you write anything. **The process `id` is not one of the five to ask about** — see Procedure step 3 for the default that replaces that question in the common case.
5. Optional **`skills/workspace/workflow-bpmn-authoring/SKILL.md`**.

## Procedure

Steps 1 through 5 are yours to work through without checking back in — a plan and a draft file are
both local and undone by nothing more than editing them again. **Step 6's deploy is the only point
that needs the user a second time**, and the IDE already forces that confirmation as a modal with no
flag to suppress it — don't manufacture an earlier "shall I continue?" on top of a gate that already
exists downstream. If something changes the plan mid-flight (the id turns out to be live, the
requirement turns out to need Java), say so and adjust — that's new information changing the answer,
not a reason to re-ask a question Input 4 already covered.

1. **Settle** the five facts plus the id default in one line of working notes (not a question) — tenant, new-or-copy, id (yours by default, see step 3), name, deploy-or-not — before doing anything.
2. **Decide whether BPMN is enough** — Extra steps, different reviewers, routing on a submitted decision and due dates are BPMN-only. Clarification loops, N-of-M quorum, custom notification text, external calls and **restricting a flow to one entity type** (the entity-type gate in `bpmn-rules.md` §17, which needs a small resolver class) need Java — that's a different skill for a different kind of change, not a slower path through this one, so hand off to `workflow-jar-customization` and say why, rather than asking whether to proceed here anyway.
3. **Default the id to the OOTB flow's own id — don't ask, FYI instead** — When the customization *is* one of the 4 fixed flows (a DCR review, a potential-match review, a delete review, an authoring review — §14), default the process `id` to that flow's existing id (`dataChangeRequestReview` for DCR, by far the most common case; `potentialMatchReview`; `deleteReview`/`recommendForDelete` for Delete, confirmed per-tenant, see below) **without asking**. If the user has already named a different id themselves, use theirs without asking. State the choice as one line of FYI, not a question: *"Using `dataChangeRequestReview` as the process id so this triggers automatically from the Hub UI's Suggest button."* Pair that FYI with the one consequence that actually matters and must never be silently hidden: **this replaces the tenant's current default flow for that object kind — every DCR on every entity type, not only the one the user asked about** — because `objectTypes`-based scoping to a single entity type is not confirmed to work from raw BPMN (see `bpmn-rules.md` §2's `dataObject` note). **If the user named an entity type ("for Product", "only Location"), do not offer them a choice between a new id and an override, and do not tell them to set `objectTypes` after import: keep the OOTB id and build the entity-type gate from `bpmn-rules.md` §17** — a resolver service task, then an exclusive gateway whose default branch is the unchanged standard review, so other entity types behave exactly as before — and word the FYI accordingly ("runs for every entity type's DCR, but only Product takes the new path"). That line is still an FYI, not a question — state it and continue, don't wait for a reply, unless the user's own request already signals they know this and want a separate, narrower id instead (in which case use theirs, and you're back to a genuinely new, unscoped-by-anything custom id — see the version-N+1 note below for that path). Check whatever id you end up with against the tenant's deployed definitions (Input 3) yourself rather than asking whether it exists — if it does, deploying creates **version N+1 of that live workflow**, not a new one; say so plainly once the draft exists, don't stop now to ask about it. For Delete specifically, read the live id from the tenant's **Process Definitions** (`deleteReview` or `recommendForDelete` — it's the one id known to vary by tenant). If you cannot confirm it because you have no API access, default to `deleteReview` and say so in the FYI line ("Using `deleteReview`; if your tenant's delete flow is `recommendForDelete`, tell me"). Never ask for a token to find out.
4. **Plan, then write — the plan is not a gate** — State the flow, each task with its `candidateGroups` **and its two required create listeners from §3 — every user task, not only the first**, each gateway with its default, and every `activiti:class`, then go straight into step 5 with it. Showing the plan lets the user catch a mistake before it's in a file; it is not a request for permission to type one — holding it open for a reply just doubles the back-and-forth over something nobody has to accept yet. Listeners are easy to type correctly once and by memory the second time; a second or third review task is the one most likely to be missing one, which is exactly why the plan calls it out per task rather than once for the workflow.
5. **Write from the skeleton** — Copy §1 of `bpmn-rules.md` in full, including the three diagram namespaces, and emit the `<bpmndi:BPMNDiagram>` section from §11. A definition with no diagram interchange executes correctly and renders as a blank canvas in every viewer, the Reltio console included. Use only the OOTB class names in §5; an invented class deploys and then fails at runtime.
6. **Invoke the command with what you already know, and let its own prompts be the only remaining questions** — each takes an argument object and prompts only for what is missing: `reltio.newWorkflowDraft` with `{ environmentName, tenantId, processId, displayName }`, `reltio.duplicateWorkflowDraft` with the same plus `sourceProcessId`, `reltio.deployWorkflow` with `{ environmentName, tenantId, processId }`. Pass `environmentName` and `tenantId` together or omit both. Two things you cannot bypass, and don't need to pre-empt by asking first: the process id is always re-validated in a prompt pre-filled with yours (if the user changes it, that is the id — use it in everything you say afterwards), and deploy always shows a modal confirmation with no flag to suppress it. If the user declines, nothing was uploaded; say so rather than retrying. If you cannot invoke commands at all, write the file at `.reltio/<environment>/<tenantId>/Workflows/bpmn/<processId>.bpmn20.xml`, reusing folder names already in the workspace — anything written elsewhere is not recognized as a draft, and the tree picks up a correct path on save. Deploying it is then the user's own next step from the tree (or a later session with command access) — do not attempt a raw `POST .../deployments` call yourself to finish the job, and do not ask for a Bearer token to do so: that call needs an authenticated tenant session that deliberately lives only in the IDE's own process memory, never on disk, so there is nothing for you to use and nothing anyone should hand you just to work around it.
7. **Check your own work silently** — Save the draft. If Reltio IDE reports diagnostics for it, fix every finding; if it does not (no Problems panel for this file), walk the twelve items of `bpmn-rules.md` §10 yourself. Either way **do not narrate the check**: no checklist recital, no "no live diagnostics here", no "I self-checked" — fix what you find and move on, and mention a problem only if you could not fix it. Every `userTask` carries both create listeners and the full §3 property set **without exception**: a task that "isn't a review" (a clarification or notification task) still needs both, or the deploy fails with errorCode 10044. Three items are yours because the editor does not check them: §10.7 (condition values match their form property exactly) and §10.10 (is this id already live) depend on facts outside the file — §10.10 is the "this becomes a new version of your live flow" clause of the FYI — and §10.12 (`accessTypes` and `validator` on every review task) is satisfied by copying §3's full block.
8. **Show the diagram** — Run **Show BPMN Diagram** (`reltio.previewWorkflowDiagram`) and have the user check the shape of the flow. It is the fastest review of work you just did.

## Outputs

Write the final reply in exactly this shape — short, plain, in this order, nothing else added. The reader is a customer or partner, not a Reltio engineer.

1. **`Skills read: <playbook names>`** — the first line, names only (e.g. `workflow-bpmn-authoring, workflow-jar-customization`).
2. **FYI, one or two sentences** — the process id you used and why, and its scope. Example: *"Using `dataChangeRequestReview` so this triggers automatically from the Hub's Suggest button. It runs for every entity type's DCR, but only Product takes the new path — all other types keep the standard review. Deploying creates a new version of your live DCR flow."* If you built the standard branch from Reltio's default shape rather than a copy of the tenant's live flow, add: *"(If your live flow is customised, tell me and I'll start from a copy of it.)"*
3. **What I built** — two to four bullets in plain words: who reviews, what happens on send-back, the BPMN file path, and — when Java is involved — the module and class names.
4. **"Shall I raise a PR for this?"** — when Java is involved; this is the one question in the whole reply. For a BPMN-only flow, the equivalent is the next step below.
5. **The next step, named** — what the user does after the PR is merged and the JAR is published: **Refresh JARs** → **Unregistered** → **Register JAR...**, then open the BPMN → **Deploy to Tenant**. For BPMN-only: show the diagram, then **Deploy to Tenant** from the tree. Name these actions exactly; "import in Workflow Modeler", "build and publish via your pipeline" or "register it with the tenant" are not acceptable substitutes. When the next step genuinely is not an IDE action (waiting on Reltio's review), say that plainly.

**Voice rules for the whole reply — and for anything you say while working:**

- Never mention playbooks, skills, rule or section numbers, deny-lists, or that any instruction contradicts another. If two pieces of guidance seem to disagree, choose the safe option silently. There is no "deviation" to announce.
- Never list the validation you ran or say what tooling was or was not available. Report a problem only if it is still unresolved, in one plain sentence.
- Never suggest local testing, a local Workflow Adapter or running `mvn` as something the user should do next. The path is: PR → registration → deploy.
- Keep internal uncertainty out of the chat and out of the files. Do not write speculative text into the BPMN (for example a `<documentation>` line claiming behaviour nobody confirmed). State a limitation only when it changes what the user gets, in one sentence without jargon.
- The plan you state before building is five lines or fewer.
